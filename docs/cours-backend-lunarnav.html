    Module 1

    Le produit en une minute

    Au pôle Sud lunaire, le Soleil reste à quelques degrés au-dessus de l'horizon et en fait le tour en un mois. La Terre, elle, oscille près de l'horizon (libration). Une crête à 20 km suffit à couper le courant d'un atterrisseur solaire ou sa liaison radio directe avec la Terre.

    Le backend répond à trois questions de planificateur de mission :

    1. Ce site, à cette date : combien d'heures de Soleil et de Terre pendant le séjour, quand est le prochain coucher, la batterie tient-elle ? (/metrics, /battery, /timeline)
    2. Le lancement glisse de N semaines : quel site devient le meilleur ? C'est la fonction phare (/fallback, alimentée par la /heatmap).
    3. Peut-on faire confiance au chiffre ? Marge d'horizon (closeCall), incertitude de position (/uncertainty), validation contre la NASA (/validation).
    Le backend ne fait que de la géométrie : direction du Soleil et de la Terre dans le ciel du site (éphéméride JPL), comparée à l'horizon réel (relief LOLA). Pas d'atmosphère sur la Lune, donc pas de réfraction : un astre est visible si et seulement s'il dépasse le relief.
    En une phrase, que fait votre backend ?
    Il calcule, pour 32 sites du pôle Sud et n'importe quelle date de 2026 à 2030, quand le Soleil et la Terre sont visibles au-dessus du vrai relief, et en déduit les fenêtres de mission, l'énergie disponible et le meilleur site de repli si le lancement glisse.
    Pourquoi Apollo 11 est-il dans la liste alors qu'il n'est pas au pôle ?
    Comme point de comparaison grand public. Il est hors de la carte LOLA du pôle (−80° à −90°), donc terrain: false : on utilise un horizon plat (HorizonMask.Flat()), et il n'est jamais classé devant un site avec du vrai relief (/ranking l'exclut, /fallback le met en dernier).
    Module 2

    Architecture : trois projets, une règle

    La solution LunarNav.slnx (.NET 11) contient trois projets de code et deux projets de tests.

    LunarNav.CoreLes mathsGéométrie, éphéméride, relief, analyse. Aucun fichier, aucun réseau, aucun HTTP. Que des fonctions pures.
    LunarNav.ApiLa porte d'entréeASP.NET Core minimal API : lit les fichiers, valide les paramètres, appelle Core, renvoie du JSON. Contient aussi les commandes precompute, validate, manifest.
    LunarNav.WebLe frontBlazor WebAssembly. Ses données statiques sont dans wwwroot/data, le même dossier que l'API lit.
    TestsDeux étagesCore.Tests teste les maths ; LunarNav.Tests démarre la vraie API en mémoire.

    La règle : Core ne connaît ni les fichiers ni le web. Program.cs ne fait pas de maths. Résultat : les mêmes fonctions (HorizonMask.Compute, Analysis.Timeline) servent à l'API, au précalcul et à la validation scientifique. Ce que la validation mesure, c'est exactement le code qui tourne en production.

    Un seul code pour trois usages. Si la validation utilisait une copie du calcul, elle ne prouverait rien sur le produit. C'est pour ça qu'on a ajouté la commande validate en C# alors qu'une version Python existait déjà.

    Pourquoi C# / ASP.NET Core et pas FastAPI ?

    Le README prévoyait FastAPI. On a choisi C# pour quatre raisons, à donner dans cet ordre :

    1. Modèles partagés avec le front. Models.cs (records SiteMetrics, HeatmapDto…) est désérialisé tel quel par le front Blazor. Un seul contrat, typé des deux côtés, pas de schéma à synchroniser à la main.
    2. Calcul lourd et parallèle. Un horizon = 720 azimuts × 3 125 pas de 80 m ≈ 2,25 millions de lectures du relief. Parallel.For utilise tous les cœurs ; en Python pur, le GIL bloque ce parallélisme et chaque boucle est des dizaines de fois plus lente.
    3. Typage strict. Les erreurs d'unités et de dates (UTC ou local) sont la première source de bugs dans ce domaine. Records immuables, DateTime avec Kind, enums SunRule et EarthRule.
    4. Un seul livrable. Une image Docker, un binaire, OpenAPI généré automatiquement.

    Python reste là où il est le meilleur : scripts ponctuels (tools/fetch_ephem.py pour JPL Horizons) et une réimplémentation indépendante qui sert de contre-vérification (tools/validation).

    Minimal API plutôt que contrôleurs

    Les 16 routes tiennent dans un seul Program.cs d'environ 290 lignes : api.MapGet("/sites/{id}/metrics", (string id, AppData data, DateTime? at, double stayDays = 14, …) => …). Les paramètres de requête sont liés et typés automatiquement, les valeurs par défaut sont dans la signature, et OpenAPI les documente. Des contrôleurs ajouteraient des classes et des attributs sans rien apporter à une API en lecture seule de cette taille.

    À quoi sert la ligne « public partial class Program; » à la fin de Program.cs ?
    Les instructions de haut niveau génèrent une classe Program interne. Cette ligne la rend publique pour que le projet de tests puisse écrire WebApplicationFactory<Program> et démarrer la vraie API en mémoire.
    Pourquoi Program.cs commence-t-il par des « if (args is ["precompute", …]) » ?
    Le même exécutable sert d'API et d'outil en ligne de commande. dotnet run -- precompute <dem> <data>, validate et manifest tournent puis quittent avant que le serveur web soit construit. Pas de deuxième projet à maintenir, et les outils utilisent forcément le même Core que l'API. Les motifs de liste C# vérifient le nombre d'arguments.

    Pourquoi une éphéméride en CSV et pas une bibliothèque (SPICE, Skyfield) ?

    On n'a besoin que de deux directions par heure. Les télécharger une fois depuis JPL Horizons donne la référence officielle (DE441), zéro dépendance au runtime et un fichier citable. Le script refuse une réponse dont l'en-tête ne contient pas MOON_ME et {East-longitude positive} : il vaut mieux planter que d'utiliser un repère faux sans le savoir. Entre deux heures, Ephemeris.At interpole (module 4).

    Pourquoi pas de base de données ?
    Toutes les données sont immuables et produites hors-ligne ; l'API ne fait que lire. Il n'y a ni écriture, ni utilisateurs, ni requêtes libres. Des fichiers JSON chargés en mémoire au premier accès sont plus rapides qu'une base, ne coûtent rien à héberger, se versionnent dans git et se vérifient par SHA-256. Une base deviendra utile le jour où on stockera des missions d'utilisateurs.
    Si on change un site dans sites.json, que faut-il relancer ?
    precompute (masques, heatmap, incertitude, puis le manifest automatiquement) et validate si le site a du relief. Sans ça, /metrics renvoie 400 « no horizon mask computed yet » pour ce site : l'API refuse de répondre plutôt que d'utiliser un horizon faux.
    Module 4

    Les maths du Core

    Conventions partout : angles en degrés, longitude positive vers l'est, latitude −90 au pôle Sud, distances en km, heures en UTC, repère lunaire Moon Mean Earth.

    1. Où est le Soleil dans le ciel du site ? (Geometry.SunAzEl)

    L'éphéméride donne le point de la Lune où le Soleil est au zénith (point sub-solaire). On le transforme en vecteur unitaire, puis on le projette sur la base locale du site : haut = vecteur du site, est = (−sin lon, cos lon, 0), nord = (−sin lat cos lon, −sin lat sin lon, cos lat). Élévation = atan2(haut, √(est² + nord²)), azimut = atan2(est, nord).

    2. La Terre, avec parallaxe (EarthAzEl)

    Le Soleil est si loin que sa direction est la même partout sur la Lune. La Terre est à ~384 000 km : sa direction change jusqu'à 0,26° selon l'endroit où on se tient. On calcule donc le vrai vecteur Terre − site en km. Son rayon apparent vaut atan(6 371 / distance) ≈ 0,95° ; celui du Soleil varie de 0,262° à 0,272° avec la distance Terre-Soleil (excentricité 0,0167).

    3. Interpoler l'éphéméride entre deux heures

    // MATH-REVIEW: never interpolate longitudes directly (359 -> 1 would pass through 180).
var va = Geometry.UnitVector(latA, lonA);
var vb = Geometry.UnitVector(latB, lonB);
var v  = va + f * (vb - va);          // puis retour en (lat, lon)
    Interpoler 359° et 1° donne 180° : le Soleil sauterait de l'autre côté du ciel. Passer par les vecteurs 3D n'a pas ce problème, et c'est ce qui permet de calculer toutes les 10 minutes avec un fichier horaire.

    4. Lire le relief (Dem)

    La carte LOLA est en projection stéréographique polaire : ρ = 2R·tan(π/4 + lat/2), x = ρ sin lon, y = ρ cos lon, pixel = centre ± x/80. La hauteur est interpolée entre les 4 pixels voisins (bilinéaire). Le signe moins sur la ligne a été vérifié sur la vraie carte : le cratère Shackleton ne montre son fond profond qu'avec ce signe.

    5. Calculer l'horizon par lancer de rayons (HorizonMask.Compute)

    Parallel.For(0, 720, i => {                  // un azimut tous les 0,5°
  for (double d = 0.08; d <= 250; d += 0.08) { // pas de 80 m = 1 pixel, jusqu'à 250 km
    P = point du relief à la distance d (grand cercle), en vrai 3D
    angle = asin((P - oeil) · haut / |P - oeil|)
    best = max(best, angle)
  }
  mask[i] = best;
});
    250 km et pas 150 : depuis un sommet, l'horizon est 2 à 5° sous l'horizontale, donc du relief plus bas et très loin reste visible. Et parce que l'œil et chaque point du relief sont de vrais points 3D, la courbure de la Lune est prise en compte sans formule à part. Un test le prouve : sur une Lune lisse, l'horizon vaut exactement l'abaissement théorique −acos(R / (R + h)) à 0,001° près.

    6. Quelle part du disque dépasse du relief ? (DiskFractionOverMask)

    Le disque est découpé en 16 bandes verticales, chacune comparée à l'horizon à son propre azimut, avec l'aire exacte du segment de cercle. La Terre fait ~1,9° de diamètre : l'horizon n'est pas plat sur toute cette largeur, et une seule comparaison au centre se tromperait. Les éclipses (la Terre devant le Soleil) réduisent ensuite sunFrac de la surface de recouvrement des deux disques.

    Essayez : le Soleil sur un horizon plat

    Déplacez le centre du Soleil par rapport à l'horizon. Rayon 0,2666°. Formule de Geometry.DiskFraction : 1 − (acos k − k√(1−k²)) / π avec k = marge / rayon.

    Comment savez-vous que les directions du Soleil et de la Terre sont justes ?
    Test unitaire contre JPL Horizons (SunAzEl_Haworth_MatchesJplHorizons) : écart inférieur à 0,01°, et 0,006° au maximum sur nos contrôles. Le test échoue si on décale de 0,1° la longitude du Soleil ou du site, donc il n'est pas trop tolérant.
    Pourquoi un pas de 80 m dans le lancer de rayons ?
    C'est la taille d'un pixel LOLA : un pas plus fin relirait le même pixel interpolé sans information nouvelle, un pas plus grand pourrait sauter une crête étroite. 720 × 3 125 pas ≈ 2,25 millions de lectures, environ une seconde en parallèle.
    Module 5

    Le moteur d'analyse (Analysis.cs)

    Tout part d'une fonction : Point(eph, site, mask, t) renvoie à l'instant t l'azimut, l'élévation et la fraction visible du Soleil et de la Terre, plus un indice de puissance. Tout le reste compte, enchaîne ou classe ces points.

    Fenêtres continues : BridgeGaps puis RunLengths

    Une fenêtre = nombre d'heures consécutives de Soleil (ou Soleil + Terre) à partir de l'atterrissage, après avoir comblé les trous de 6 h ou moins entourés de Soleil. Les trous au début et à la fin ne sont jamais comblés. Viable = fenêtre ≥ durée du séjour.

    Les métriques d'un séjour (Metrics)

    • Pourcentages et nuits : pas de 10 minutes sur la durée du séjour (éphéméride interpolée).
    • Fenêtres : pas d'une heure, jusqu'à 60 jours après l'atterrissage. Si la fenêtre touche la fin des 60 jours ou des données, WindowLowerBound dit « au moins ».
    • Prochains lever et coucher (NextCrossing) : recherche heure par heure, puis affinage par pas de 10 minutes dans l'heure du changement.
    • Marge : avec marginDeg = 0,2, tout est recalculé avec l'horizon monté et descendu de 0,2°. Résultat : SunPctRange, HoursToSunsetRange, et CloseCall = true si le verdict viable change.
    • DSN : DsnPct = part du séjour où la Terre est en vue et la Lune est à plus de 10° au-dessus de Goldstone, Madrid ou Canberra (théorie lunaire basse précision, ~0,3°).

    Le repli si le lancement glisse (BestFallback)

    La heatmap donne, pour chaque site et chaque jour, la meilleure fenêtre. Pour la date glissée, chaque site reçoit sa fenêtre, son verdict avant et après, le jour viable le plus proche, la robustesse (part des jours viables à ±2 semaines) et la tolérance au glissement. Tri :

    entries.OrderByDescending(e => e.Terrain)        // relief réel d'abord
       .ThenByDescending(e => e.WindowHours)       // plus longue fenêtre
       .ThenBy(e => e.LongestDarkHours)            // nuit la plus courte
       .ThenByDescending(e => e.Robustness)        // le moins sensible à la date

    Le classement robuste (RobustRanking)

    Classer des sites demande de pondérer Soleil, Terre et plus longue nuit. Au lieu d'imposer des poids, on tire 2 000 pondérations au hasard, uniformément sur le simplexe (wᵢ = −ln(1−U) puis normalisation), avec une graine fixe (42) pour que la réponse soit stable. Pour chaque site : % de tirages où il est premier, rang moyen, et optimum de Pareto (aucun autre site n'est meilleur sur les trois critères à la fois). Les sites sans relief sont exclus.

    La batterie (SimulateBattery)

    Heure par heure, batterie pleine au départ : production = indice × 1 361 W/m² × surface × rendement ; consommation constante. Par défaut 5 000 Wh, 150 W, 2 m², 28 %, plancher 20 %. L'indice suppose un panneau vertical qui suit le Soleil (sunFrac × cos(élévation)), le bon choix quand le Soleil rase l'horizon. Batterie minimale pour survivre = déficit maximal / (1 − plancher).

    Incertitude et obstacles

    Uncertainty recalcule tout en 40 points autour du site (8 à 100 m, 16 à 250 m, 16 à 500 m), chacun avec son propre horizon : un atterrisseur ne se pose jamais au mètre près. Blockers compare les heures de Soleil avec un horizon plat et avec le vrai, donne les 3 secteurs de 10° qui coûtent le plus, et le gain d'un mât de 10 m sur un de 2 m.

    Que veut dire « close call » ?
    Le verdict « viable » change quand on monte ou descend tout l'horizon de 0,2°, l'ordre de grandeur de notre erreur de relief. Le front l'affiche en RISKY : viable, mais pas avec certitude.
    Pourquoi 2 000 pondérations et une graine fixe ?
    2 000 tirages suffisent pour que les pourcentages se stabilisent pour une trentaine de sites, et le calcul reste instantané. La graine fixe garantit que deux appels identiques donnent le même classement : un jury qui recharge la page ne doit pas voir le classement changer.

    L'API, endpoint par endpoint

    Base en production : https://lunarnav-api.onrender.com. La racine / redirige vers Swagger, le schéma est sur /openapi/v1.json. Choisissez un endpoint :

    Conventions communes

    • Dates en UTC. Une date sans Z arrive en Unspecified : la fonction Utc() la traite comme UTC. Une date locale est convertie. Pas de date = maintenant.
    • Mât = 2 ou 10 m sur les routes précalculées (BadMast), car seuls ces masques existent. /custom accepte 1 à 20 m puisqu'il calcule l'horizon en direct.
    • Codes d'erreur. 400 = paramètre invalide ou date hors 2026–2030 ; 404 = site inconnu ou donnée pas encore produite ; 503 = carte du relief absente (seulement /custom).
    static IResult Guard(Func<IResult> f)
{
    try { return f(); }
    catch (Exception ex) when (ex is ArgumentException or InvalidOperationException)
    { return Results.BadRequest(ex.Message); }   // l'erreur de l'appelant devient un 400
}
    Core lance des exceptions claires (ArgumentOutOfRangeException « utc is outside the ephemeris range »). L'API ne revalide pas tout : Guard transforme ces exceptions en 400 avec le message. Toute autre exception reste un 500, parce que c'est un vrai bug et qu'il ne faut pas le masquer.
    Pourquoi passer par votre serveur pour /moon au lieu d'appeler la NASA depuis le navigateur ?
    Dial-A-Moon n'envoie pas d'en-têtes CORS, donc le navigateur ne peut pas l'appeler. Le proxy ajoute un cache par heure, un délai max de 3 s et un repli local calculé depuis notre éphéméride si la NASA est lente, en panne, ou si la date est après 2026 (la NASA renvoie alors silencieusement 2026). Un échec n'est pas mis en cache, pour réessayer au prochain appel.
    Pourquoi CORS est-il ouvert à toutes les origines ?
    L'API est publique et en lecture seule : pas de cookies, pas de compte, pas de secret. Le front est servi depuis une autre origine. AllowAnyOrigin n'expose donc rien de plus que ce que curl voit déjà. Le vrai risque n'est pas CORS mais la charge (module 10).

    Mémoire, cache et concurrence

    AppData est un singleton : une seule instance pour toutes les requêtes.

    DonnéeQuand chargéeMécanisme

    Charger 115 Mo sur 512 Mo de RAM

    var dn = new short[7600 * 7600];
file.ReadExactly(MemoryMarshal.AsBytes(dn.AsSpan()));   // lu directement dans le tableau final

    Lire les octets dans un byte[] puis les convertir créerait deux copies (230 Mo). MemoryMarshal.AsBytes voit le short[] comme des octets : une seule copie. Le plan gratuit de Render a 512 Mo. La taille est vérifiée avant (7600 × 7600 × 2 = 115 520 000 octets).

    Parallélisme dans le calcul

    Parallel.For sur les 720 azimuts, sur les sites (heatmap, classement) et sur les points d'incertitude (limité à 4). Chaque itération écrit dans sa propre case du tableau : pas de verrou nécessaire. Dans Ranking, la date est vérifiée avant le Parallel.For : une exception dans une boucle parallèle arrive emballée dans une AggregateException, que Guard ne reconnaîtrait pas, d'où un 500 au lieu d'un 400.

    L'API peut-elle passer à plusieurs instances ?
    Oui, sans changement : elle est sans état. Les caches sont de simples copies en mémoire de fichiers immuables embarqués dans l'image Docker. Chaque instance les recharge à son rythme et elles donnent toutes les mêmes réponses.
    Module 8

    Validation scientifique et tests

    La commande validate exécute le vrai code du produit (HorizonMask.Compute + Analysis.Timeline) sur les 31 sites avec relief, heure par heure sur les 43 825 heures, et compare au produit 69 de la NASA PGDA (cartes d'illumination moyenne de E. Mazarico).

    Écart médian : 0,78 point (Soleil), 0,74 point (Terre). Corrélation 0,970 et 0,996. Les 8 écarts de plus de 5 points sont tous sur des crêtes ou des bords de plateau, où la valeur NASA elle-même varie de 20 à 60 points d'un pixel au voisin.

    Seuils écrits avant le calcul. thresholds.json a été commité (commit 8ed64ee) avant la première exécution du C#. On ne peut donc pas les avoir ajustés aux résultats. Les échecs sont publiés tels quels.

    Les trois points à connaître par cœur

    1. Pourquoi à 0 m ? Les cartes PGDA sont des cartes de surface. Les valeurs du produit à 2 et 10 m sont aussi publiées dans validation.json.
    2. Verdict par site. OK si l'écart ≤ 5 points ; « expliqué » si notre valeur est dans la fourchette 3×3 pixels de la NASA (ou la NASA dans nos 8 voisins à 80 m), à 5 points près ; sinon « problème ».
    3. Contrôles négatifs. On fausse volontairement le calcul : s'il donne encore un bon accord, la comparaison ne distingue pas le vrai du faux. Deux sur trois passent. Explication : une moyenne sur 5 ans ne dépend presque pas du moment où le Soleil passe, puisqu'il fait le tour de l'horizon. Cette comparaison valide donc l'horizon, pas le calendrier. Le calendrier est validé par le test JPL Horizons à 0,01°.

    Pourquoi l'écart C# / Python dépasse le seuil

    Depuis la PR 26, le C# compare 16 bandes du disque à l'horizon réel ; le Python compare le disque entier à l'horizon pris en son centre. La Terre étant environ 4 fois plus large que le Soleil, l'effet y est plus fort (0,42 contre 0,08). Ce changement était connu et écrit dans les seuils avant le calcul. On n'a pas modifié le seuil après coup.

    Qu'est-ce qui n'est PAS validé ?
    Le relief lui-même (la NASA et nous utilisons LOLA : on valide la méthode, pas la donnée). La période (5 ans chez nous, 18,6 ans chez la NASA ; un site varie de 2 à 3 points d'une année à l'autre). Les hauteurs 2 et 10 m (pas de carte NASA ; seule la comparaison à Gläser et al. 2014 sur la Connecting Ridge, écart de −2,5 et −2,2 points). Et les crêtes, lissées par le pixel de 80 m.
    Deux contrôles négatifs sur trois passent : votre validation ne vaut rien ?
    Elle vaut pour ce qu'elle mesure : l'horizon. Le contrôle miroir, qui casse l'horizon, échoue bien. Les deux autres cassent le calendrier, que la moyenne sur 5 ans ne voit pas. Le calendrier est couvert par un autre test, JPL Horizons à 0,01°, qui échoue avec un décalage de 0,1°. On l'a écrit dans le document plutôt que de retirer ces contrôles.

    Déploiement et exploitation

    branchePR vers devCI : restore, build Release, 97 tests. Approbation du propriétaire obligatoire.
    releasePR dev → mainmain n'accepte que des PR venant de dev.
    RenderBuild DockerBlueprint render.yaml, déploiement automatique à chaque merge dans main.

    Le Dockerfile, ligne par ligne

    FROM mcr.microsoft.com/dotnet/sdk:11.0 AS build          # étape 1 : compiler
COPY *.csproj …  ;  RUN dotnet restore                     # seulement les .csproj : restore reste en cache
COPY sources …   ;  RUN dotnet publish -c Release
RUN curl … ldem_80s_80m.img && [ taille = 115520000 ] || rm -f …   # relief, toléré s'il échoue

FROM mcr.microsoft.com/dotnet/aspnet:11.0                  # étape 2 : runtime seul, sans SDK
COPY --from=build /app . ; COPY dem/ ; COPY wwwroot/data/ /app/data/
ENV DataDir=/app/data DemPath=/app/dem/LDEM_80S_80M.IMG ASPNETCORE_HTTP_PORTS=10000
USER app                                                   # pas root
    Multi-étapes : l'image finale ne contient ni SDK ni sources. Copier les .csproj avant le code garde la couche restore en cache tant que les dépendances ne changent pas. La carte LOLA (115 Mo) est trop grosse pour git : elle est téléchargée au build, avec vérification de taille. Si le téléchargement échoue, seul /custom est coupé (503) : le reste de l'API fonctionne.

    Render, plan gratuit

    • Région Ohio (la plus proche de Toronto), healthCheckPath: /api/health, autoDeploy: true depuis main.
    • 512 Mo de RAM (d'où la lecture du relief en une seule copie).
    • Le service s'endort après 15 minutes sans requête ; le réveil prend ~60 s. Le workflow keep-alive.yml appelle /api/health toutes les 5 minutes (GitHub peut décaler un cron de quelques minutes, d'où la marge).

    Garde-fous Git

    owner-approval.yml : la PR est verte seulement si le propriétaire l'a approuvée sur le dernier commit, ou a posé le label approved. Un nouveau commit retire le label : il faut réapprouver. Un second job refuse toute PR vers main qui ne vient pas de dev.

    Pourquoi Render et pas Azure, AWS ou Vercel ?
    Gratuit, déploie directement un Dockerfile, et se configure par un fichier dans le dépôt (render.yaml) avec déploiement automatique sur main. Vercel vise le front et les fonctions courtes, pas un serveur .NET qui garde 115 Mo en mémoire. Azure ou AWS auraient marché mais demandent plus de configuration pour un hackathon. Limites assumées : mise en veille et 512 Mo.
    Que se passe-t-il si le build Docker n'arrive pas à télécharger la carte LOLA ?
    Le fichier partiel est supprimé, le build continue, l'API démarre. AppData.Dem vaut null et POST /api/custom renvoie 503 « terrain map not loaded ». Tout le reste utilise les masques précalculés et marche normalement.

    Limites assumées

    Un jury fait confiance à une équipe qui connaît ses limites. Celles-ci sont toutes écrites dans /api/about ou dans docs/validation.md, sauf la dernière ligne, à connaître quand même.

    LimiteEffetCe qu'on ferait ensuite

    Pas d'authentification ni de limite de débit/custom calcule un horizon (~1 s de CPU) à chaque appel : quelques appels simultanés saturent le plan gratuit.AddRateLimiter d'ASP.NET Core, cache par point arrondi, file d'attente.
    Que se passe-t-il si 100 personnes appellent /custom en même temps ?
    Chaque appel lance un lancer de rayons parallèle d'environ une seconde de CPU, sur une petite machine gratuite. Les réponses ralentiraient fortement, voire expireraient ; rien ne protège ce endpoint aujourd'hui. Les autres routes lisent du précalculé et tiennent mieux. La correction est connue et courte : un limiteur de débit sur /custom et un cache des horizons par coordonnées arrondies au pixel.
